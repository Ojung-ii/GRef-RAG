## CPU verification scope

The verifier aggregates saved EM/F1 records and context-token counts, derives dataset-level and macro F1/1K, and checks the published values at their displayed precision. It replays the main, matched-budget, ablation, Llama, News, seed/fusion, and candidate-cap statistics using the recorded 10,000-draw policies. Separate Holm families apply to the main analysis, primary ablations, heterogeneous views, News, seed/fusion, and candidate cap. Individual percentile intervals describe paired query sampling. [Verification command](RUN_MANIFEST.md#cpu-verification) · [Paper values](paper_values.csv)

The released ledgers expose query IDs, scores, counts, and hashes. The public CPU verifier takes the saved per-query scores as inputs. Answer-level rescoring requires prediction text and the benchmark references, and the `evaluate` command accepts these inputs. Prediction hashes let readers compare fresh answers against the GRef-RAG reference records. Some published values use archived measurement summaries, including offline costs and parts of native token accounting. Historical request parameters, original Run IDs, and exact executed source revisions are retained where supported by the surviving records. [Manifest](run_manifest.csv) · [Evaluation guide](../docs/evaluation.md)

The manuscript presents Figure 1 as an illustration of evidence organization for a comparison question. The two archived QA protocols assign different scores to that question. The larger panel's exact source and generation protocol remain unverified.

Fresh GRef-RAG inference uses the supplied configurations. Historical baseline indexing, generation, and some supplementary controls require their original implementations and execution metadata. The two main prompt settings and stored budget controls are the release's fresh inference scope. The separate HotpotQA reproduction distinguishes frozen-context replay from a fresh index build and end-to-end execution.
